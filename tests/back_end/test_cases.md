**测试用例设计 (针对 `hill.world`)**

我们将设计几组测试，重点关注不同区域和不同 `Ps` 值下的表现。

**通用操作：**

*   启动 Gazebo 加载 `hill.world` 和原始类车机器人模型。
*   启动 `uneven_planner` 的所有必要节点。
*   将 `ALMTrajOpt` 节点的日志级别设置为 DEBUG。
*   所有规划操作的输出日志保存到不同的文件。
*   使用 Python 脚本分析日志。

**测试用例 1：在山脚平坦区域规划直线**

*   **目标：** 验证在平坦区域，打滑成本接近于零。
*   **场景：** 在 `hill.world` 中找到一块相对开阔和平坦的区域（例如，山脚下）。
*   **操作：**
    1.  **对照组 (Ps=0)：** 设置 `param_Ps_slip_weight: 0.0`。规划一条在该平坦区域内的短直线路径。收集日志 `hill_flat_Ps0.log`。
    2.  **实验组 (Ps=1.0)：** 设置 `param_Ps_slip_weight: 1.0`。规划完全相同的直线路径。收集日志 `hill_flat_Ps1.log`。
*   **预期结果/KPI：**
    *   **日志分析 (Python 脚本)：**
        *   对于 `hill_flat_Ps0.log` 和 `hill_flat_Ps1.log`，在平坦区域对应的日志行中，解析出的 `sin_phix_value` 和 `sin_phiy_value` 都应接近 0。
        *   因此，Python 脚本计算的 `expected_slip_cost_step` 都应接近 0。
        *   C++ 代码打印的 `slip_cost_delta`（或 `slip_cost_step`）也应接近 0。
        *   **KPI 1 (成本计算准确性 - 平地):** Python 脚本报告的 C++ 计算与 Python 计算之间的“Mismatch”差异应小于 `1e-5` (对于接近零的值，主要看绝对差异)。
    *   **轨迹对比：** 两条轨迹应该几乎完全相同，规划时间也应相似。

**测试用例 2：沿固定坡度的山坡规划直线（上坡/下坡）**

*   **目标：** 验证在有坡度的区域，打滑成本计算正确，并观察不同 `Ps` 值对轨迹的初步影响。
*   **场景：** 在 `hill.world` 中找到一段坡度相对均匀的直坡道。
*   **操作：**
    1.  **对照组 (Ps=0)：** 设置 `param_Ps_slip_weight: 0.0`。规划一条沿该坡道直上或直下的路径。收集日志 `hill_slope_Ps0.log`。
    2.  **实验组 1 (Ps=1.0)：** 设置 `param_Ps_slip_weight: 1.0`。规划完全相同的路径。收集日志 `hill_slope_Ps1_low_weight.log`。
    3.  **实验组 2 (Ps=10.0 或更高，需要尝试)：** 设置 `param_Ps_slip_weight: 10.0`。规划完全相同的路径。收集日志 `hill_slope_Ps10_high_weight.log`。
*   **预期结果/KPI：**
    *   **日志分析 (Python 脚本)：**
        *   在坡道区域对应的日志行中，解析出的 `sin_phix_value` (如果沿x方向坡) 或 `sin_phiy_value` (如果沿y方向坡) 或两者组合应有显著的非零值。这些值在同一坡段应相对稳定。
        *   **KPI 2 (成本计算准确性 - 坡地):** 对于 `hill_slope_Ps1_low_weight.log` 和 `hill_slope_Ps10_high_weight.log`，Python 脚本报告的 C++ 计算与 Python 计算之间的“Mismatch”差异应小于 `1e-5`。
        *   **KPI 3 (打滑成本随 Ps 变化):** 比较 `hill_slope_Ps1_low_weight.log` 和 `hill_slope_Ps10_high_weight.log` 中，由 Python 脚本独立计算的 `expected_slip_cost_step` 的平均值或总和。`Ps=10.0` 时的总打滑成本应该大约是 `Ps=1.0` 时的 10 倍（如果轨迹和速度变化不大的话）。
    *   **轨迹对比 (RViz 观察与数据分析)：**
        *   **KPI 4 (轨迹形态变化 - 视觉):** 比较三条轨迹。当 `Ps` 增大时，规划出的轨迹是否在坡道上**规划了更低的速度**？或者，如果附近有更平缓的绕行路径（虽然我们这里强制走直线），它是否会尝试略微偏离以寻找更低坡度（这在纯直线规划中不明显）？
        *   **KPI 5 (规划速度变化 - 量化):** 从日志中提取规划轨迹上各点的速度 `current_velocity` (即 `vx`)。比较对照组和实验组在坡道上的平均速度或最大速度。实验组的速度是否显著低于对照组？
        *   **(次要) 规划时间/长度：** 记录规划时间、轨迹长度、Jerk成本的变化。增加 `Ps` 是否导致规划时间略微增加或轨迹长度略微变化？

**测试用例 3：跨越山丘的复杂路径**

*   **目标：** 观察在更复杂的路径上，不同 `Ps` 值对路径选择的宏观影响。
*   **场景：** 在 `hill.world` 中，选择一个需要明显上下坡才能到达的起点和终点。
*   **操作：**
    1.  **对照组 (Ps=0)：** 设置 `param_Ps_slip_weight: 0.0`。规划路径。收集日志和轨迹。
    2.  **实验组 (Ps=合适的正值，例如通过用例2调优的值)：** 设置 `param_Ps_slip_weight`。规划路径。收集日志和轨迹。
*   **预期结果/KPI：**
    *   **KPI 6 (复杂路径选择差异 - 视觉):** 在 RViz 中同时显示两条轨迹。`Ps>0` 时的轨迹是否明显更倾向于选择坡度较缓的路径，即使这意味着路径可能更长或更曲折？
    *   **KPI 7 (打滑风险指标对比 - 量化):** 对两条轨迹，使用 Python 脚本（或修改它）计算整条轨迹的**总打滑风险积分 `Σ (Slope * v)² * dt`**。`Ps>0` 时的总打滑风险积分应该显著低于 `Ps=0` 时。
    *   **(次要) 轨迹长度、时间、平滑度对比。**

**测试报告应包含的内容：**

对于每个测试用例，您的“测试报告”应该包含：

1.  **测试用例描述：** 场景、起止点、使用的 `param_Ps_slip_weight` 值。
2.  **Python 脚本验证结果：** 是否所有采样点的 `slip_cost_step` 计算都与 C++ 日志中的值匹配（或在可接受误差内）？是否有 Mismatch？
3.  **量化 KPI 数据：** 上述 KPI 的具体数值和对比。
4.  **RViz 截图或视频片段：** 清晰展示轨迹的视觉差异。
5.  **简要分析和结论：** 总结观察到的现象，判断打滑成本项是否按预期工作。
